# IPC / RPC 通信方案 v2 — 需求规格 (spec.md)

> 所属系统：[IPC / RPC 通信子系统](../../systems/rpc-communication.md)
> 状态：**已实现（Phase 0）**。方案见 [design.md](./design.md)，实现与验收记录见 [tasks.md](./tasks.md) / [check.md](./check.md)。

## 1. 背景：设计对象是整套 IPC 通信方案

渲染层（web）↔ 主进程（electron-main）之间只有**一套**通信机制，它统一解决四件事：
寻址、数据编码、错误、生命周期；并按调用形态覆盖四种交互模式：
Unary / Server Streaming / Client Streaming / Bidi。

**流式通信不是独立子系统，只是这套方案覆盖的场景之一。**
本次变更的设计对象是整套通信方案的 v2 形态；其中具体动工的部分，
是把 Server Streaming 模式从 v1 原型补完到与 Unary 同等的机制完成度。
Sink、终局状态机、取消这些原语属于通信机制的"生命周期"层，
未来 Client Streaming / Bidi 与 terminal 等服务直接复用，不为流式所私有。

### 1.1 v1 已落地的部分

- 单通道 dispatch（`rpc:invoke` + `{service, method, args}` 寻址）与服务注册表
- preload 哑管道（invoke / onStream）、web 侧双层 Proxy 客户端
- Unary 响应信封 `RpcResponse<T>` 与结构化错误
- Server Streaming v1：streamId 多路复用、`next/return/throw` 三帧、生成器泵、
  `__stream.cancel` 取消链路、消费端句柄与自动清理

### 1.2 v1 流式场景暴露的缺陷（本次演进的直接动因）

- 流的终局由 AsyncGenerator 的 `return / throw` 隐式产生，生产端没有显式的
  "我结束了 / 我失败了"调用入口
- 业务失败没有机制级位置：Agent 的 LLM 报错、超步数是 yield 一个业务事件后正常 return，
  协议帧仍是成功（`return`），消费端必须额外订阅业务事件才能感知失败
- 取消同时有两种表达（协议层 `throw(ABORTED)` + 业务事件 `done{reason:'aborted'}`）
- 回调驱动的事件源（`child_process`、pty、SSE 回调）无法自然产出流，
  只能反向包一层 AsyncGenerator

## 2. 本次范围

| 方案组成 | v1 现状 | v2 本次动作 |
| --- | --- | --- |
| 寻址与单通道 dispatch | ✅ 已落地 | 不变 |
| preload 哑管道 / 客户端 Proxy | ✅ 已落地 | 不变（句柄类型随协议演进） |
| Unary 信封 | ✅ 已落地 | 行为不变；错误结构与流终局统一为单源同形状类型 |

| Client Streaming / Bidi | 🔲 未开始 | **不实现**；协议设计不得为其制造障碍（复用同一套标识/终局/取消概念） |

## 3. 目标

跨模式（整套方案层面）：

- 错误结构在 Unary 信封与流终局之间**同形状、单源类型**，消费端共用错误处理逻辑
- 调用标识、终局、取消是通信机制的统一概念：当前服务于 Unary / Server Streaming，
  未来 Client Streaming / Bidi 可直接长入，不另起炉灶
- 机制与业务解耦：协议中不出现 Agent 专属概念，任何服务零成本使用

Server Streaming 模式补完：

- 生产端（主进程服务）获得显式原语：推数据、正常结束（可带结果）、失败结束（可带错误码与数据）
- 消费端（渲染层）获得唯一终局入口：一个回调穷尽"完成 / 失败 / 取消"三态
- **终局唯一**由句柄内部状态机保证（exactly-once），不依赖业务代码自律
- 拉模式源（AsyncGenerator）与推模式源（回调事件）都能接入，且共用同一套终局机制
- 取消信号从消费端可达生产端；取消是独立终局态，不与失败混为一谈
- 终局后资源（注册表、帧监听、回调）必然清理，无泄漏

## 4. 详细需求

> 以下 F1–F24 描述 Server Streaming 模式的机制需求；F18/F22 同时约束整套协议。

### 4.1 生产端原语

- F1：服务方法必须能拿到一个**生产端流句柄（Sink）**，无需自行准备 AsyncGenerator
- F2：Sink 提供推数据操作，可被回调驱动源在任意时机调用（如 `child.stdout.on('data')`）
- F3：Sink 提供显式**正常结束**操作，可携带一个可选的终局结果（如退出码、统计信息）
- F4：Sink 提供显式**失败结束**操作，参数为结构化错误（错误码 + 消息 + 可选数据），错误码支持服务自定义
- F5：Sink 提供注册**取消钩子**的操作，消费端取消时钩子被触发（用于 kill 子进程 / `agent.abort()`）
- F6：拉模式源必须可直接接入：传入 AsyncGenerator 时，其 next / return / throw 由机制自动映射为推数据 / 正常结束 / 失败结束

### 4.2 消费端原语

- F7：流式方法调用必须**同步**返回消费端句柄，事件订阅先于任何数据帧到达，不丢早期事件
- F8：句柄提供按事件类型的订阅 / 单次订阅 / 退订
- F9：句柄提供**唯一终局回调**，终局信息为穷尽三态的判别结构：完成（含结果）/ 失败（含结构化错误）/ 已取消；
  类型系统必须强制消费方处理（或显式忽略）三种状态，不允许"只处理成功"就通过编译
- F10：句柄提供取消操作；取消是终局的一种，不是异常抛出

### 4.3 终局状态机（机制保证项）

- F11：每条流有明确状态：`open → closed`，closed 又分 completed / failed / aborted 三态
- F12：**终局恰好一次**：正常结束、失败、取消三条路径竞争时 first-wins；终局后的重复调用静默无效，
  绝不发出第二个终局信号
- F13：终局后再推数据必须被机制丢弃（推数据操作返回是否被接受，供调用方自查）
- F14：到达终局时机制负责：发送终局帧、清理流注册表、清理两侧订阅；业务无需手动清理
- F15：生产端程序故障（handler 抛异常、泵意外中断）必须由机制兜底成 failed 终局，不允许流悬挂

### 4.4 协议

- F16：流仍由 `streamId` 标识，支持多流并存与帧的精确归属
- F17：数据帧与终局帧在协议上可区分；终局帧承载三态判别信息与可选结果 / 错误数据
- F18：取消继续走机制保留方法（不占用业务契约），其语义与 v1 保持兼容思路；
  通道与帧的划分必须能被未来反向流（client-stream / bidi）沿用
- F19：全部帧载荷可结构化克隆，错误不依赖 JS Error 跨进程传递

### 4.5 类型契约

- F20：契约中流式方法签名同时声明**事件类型**与**终局结果类型**，两端均可推导
  （如 `run(cmd): RpcStream<TermEvent, { exitCode: number }>`）
- F21：契约类型只描述消费端视图；生产端 Sink 类型是其超集，服务实现类 `implements` 契约时结构兼容
- F22：错误结构类型在 shared 单源，unary 信封与流终局共用

### 4.6 可测试性

- F23：终局状态机与帧推送逻辑不依赖 Electron，使用假服务 / 假推流接口即可单测
- F24：以下竞态必须有测试覆盖：终局竞争 first-wins、终局后推数被丢弃、取消与结束同时发生、
  生成器抛异常兜底、终局后注册表清理

## 5. 非目标（本次不做）

- 背压 / 慢消费者治理（高吞吐场景暂由服务侧合帧）
- 渲染层作为生产端（client-stream / bidi；terminal 输入二期设计，仅要求本次协议不为其制造障碍）
- 流的持久化、断线重连、跨窗口广播
- 空闲超时看门狗（若未来加，终局仍归 failed 态，不新增状态）
- Agent 业务层的更多交互（工具确认门控等不在本次范围）

## 6. 验收方向

详细验收清单见 [check.md](./check.md)；Phase 0 实现任务拆解见 [tasks.md](./tasks.md)。
（Phase 1 抽包 / 更名不在本次验收范围。）

- 用一个回调驱动的假源（事件 + 显式 error）与一个 AsyncGenerator 源分别验证同一套机制
- 任意一条流在测试中断言：终局帧恰好一个、终局后无任何后续帧、注册表无残留
- 消费端 mock 渲染层验证三态终局回调与自动退订
- `pnpm typecheck` 下：漏处理终局三态、契约与实现签名漂移均编译报错
- Unary 链路行为零回退：信封拆包、RpcError 抛出、既有 config/file 服务冒烟不变
- Agent 接入改造后，现有 `chat.send` 冒烟链路（流式输出 / 停止 / 错误提示）行为不回退
